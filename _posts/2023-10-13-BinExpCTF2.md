# Initial setup and enumeration

After downloading the `challenge_2` executable and modifying the file permissions, I did a little bit of enumeration to see what the executable was, what protections were in place, and what it does, generally.

![Identifying the Challenge Two binary.]({{ site.baseurl }}/assets/img/BE2/01-file.png)

![Checking the binary's exploit mitigations.]({{ site.baseurl }}/assets/img/BE2/02-checksec.png)

Same setup as before, except now there is a stack canary and the NX bit is set. By default, on Linux systems, the heap is not executable either. At first, I left ASLR active on my system, but this would change later.

Moreover, this program takes a single file as an argument. What did the file do? Was there a specific format which the program required? I first tried running the program with an empty file, but that seemingly did nothing. From there, I decided to crack open the hood and get to reversing.

# Reversing

No debugging symbols, once again. So, at least initially, I opted to use Ghidra for some static analysis. GDB would feature later.

Starting from the top, it was relatively easy to find the main function using similar logic to that used when looking into `challenge_1`.

![Locating main from the program entry point.]({{ site.baseurl }}/assets/img/BE2/05-main.png)

The first few lines of code were rather obvious insofar as what they were doing: loading the stack canary onto the stack, and then checking that the number of arguments is two.

![The main function prologue and argument-count check.]({{ site.baseurl }}/assets/img/BE2/06-main-prologue.png)

What followed was code that checked if the supplied argument was `-h`, in which case it would jump to the code that prints the usage, then exits.

![Checking for the help argument.]({{ site.baseurl }}/assets/img/BE2/07-help-check.png)

Otherwise, execution continues to the "main" code. The application would first try to open the file provided. Once that succeeds, it would allocate `0x50` - 80 bytes - with `malloc()`, presumably for the contents of the file.

![Opening the supplied file and allocating the input buffer.]({{ site.baseurl }}/assets/img/BE2/08-open-and-allocate.png)

Some function - which I later renamed to `processConfigFile`, so I will refer to it as such from this point onwards - is called with parameters like so:

```c
processConfigFile(buf, fd);
```

Here, `buf` refers to the allocated buffer, and `fd` refers to the file descriptor for the file which was just opened. Naturally, `processConfigFile` was what I chose to reverse next.

Firstly, the supplied file descriptor and memory-buffer pointer are saved to local variables within the function. Then, a pointer to some function is saved at offset `+0x48` from the base of the allocated memory buffer. I had a feeling that that could pose a problem.

![A callback stored near the end of the heap buffer.]({{ site.baseurl }}/assets/img/BE2/09-callback.png)

Next, the program would initialize a local integer value to two, and two word-size variables to zero, before it would attempt to read two bytes from the configuration file.

![Initialising the parser's local values.]({{ site.baseurl }}/assets/img/BE2/10-parser-init.png)

Ghidra had the code for this specific function presented a bit weirdly to me, so I corroborated what I was seeing with GDB.

![The initial two-byte read in GDB.]({{ site.baseurl }}/assets/img/BE2/11-first-read.png)

It became clear from the assembler code that the program would use the two bytes read from the configuration file as a size indicator. It would then try to read that many bytes from the file into the previously allocated buffer.

![Using the attacker-controlled value as a read size.]({{ site.baseurl }}/assets/img/BE2/12-sized-read.png)

At this point, from a defensive-security perspective, we would have a problem. More on that later.

Another read is done, this time only reading two bytes. Those bytes are compared to data held within the program's memory.

![Reading the next marker from the file.]({{ site.baseurl }}/assets/img/BE2/13-second-read.png)

![Comparing the marker.]({{ site.baseurl }}/assets/img/BE2/14-marker-check.png)

If the two bytes match `rR`, a second iteration of what just occurred is triggered: two more bytes are read and used as the size indicator for a further read.

![The rR marker stored by the program.]({{ site.baseurl }}/assets/img/BE2/15-marker.png)

![The parser's repeated read sequence.]({{ site.baseurl }}/assets/img/BE2/16-parser-flow.png)

At this point the purpose of the function was clear. It was doing some sort of processing of the configuration file. The remainder of the function would ultimately return the number of bytes read from it.

Coming back to the main function, I noted that the return value from `processConfigFile` was stored in a local variable.

![Storing the parser's return value.]({{ site.baseurl }}/assets/img/BE2/17-return-value.png)

What follows is code which effectively adjusts the stack pointer to account for the data read from the configuration file.

![Adjusting the stack pointer.]({{ site.baseurl }}/assets/img/BE2/18-stack-adjustment.png)

What came after the stack-pointer adjustment is where things got particularly interesting: a memory-copy operation writes our data from the configuration file onto the stack, starting from the current stack pointer. Then, the pointer at `buffer + 0x48` is called, with `buffer` as its first and only parameter.

![Copying the parsed data onto the stack.]({{ site.baseurl }}/assets/img/BE2/19-stack-copy.png)

![Calling the function pointer from the heap buffer.]({{ site.baseurl }}/assets/img/BE2/20-indirect-call.png)

I spent some time reversing the other two relevant functions: the initial callback and the function invoked later. Those functions were not all that helpful for exploitation. At a very high level, the initial callback prints buffer data at a given offset, while the other function sets up a socket connection and sends a GET request to some server.

# The vulnerability

The vulnerability comes down to two things:

* Not validating the size supplied from the configuration file.
* Storing a function pointer insecurely.

The exploit I would later develop could be thwarted by eliminating either component. If the program were used as intended, it would not be a problem, but a malformed configuration file - supplied intentionally or by accident - would create an issue.

If I had to provide a recommendation to the developer, I would suggest dealing with both issues:

* If it is absolutely necessary to let the user specify the size of the data to be read, validate it. Ensure that the supplied size is not above or below a defined threshold.
* Avoid storing function pointers in user-controlled memory buffers.

# Failed exploitation with ASLR active

As ASLR was active when initially trying to exploit the identified vulnerability, successfully spawning a shell proved notably difficult when, in addition to ASLR, there was NX and a stack canary.

I explored the available gadgets before realising there was no way I could think of to exploit the vulnerability while ASLR randomised the base address of every shared-object library. I tried altering `RSP` relative to a shared-library address, executing code on the heap - which did not work because the heap was not executable - and building a ROP chain from gadgets in `challenge_2`.

After exhausting the options I could think of, I opted to disable ASLR.

# Exploitation

After exploring for a bit, I found that the simplest and most reliable attack vector was a classic ret2libc-style attack. When the overwritten pointer is called, `RDI` holds a pointer to the first payload from the configuration file. I supplied `/bin/sh` as the argument to `system()`.

Null bytes were acceptable in this case because the input was supplied by a file-read operation, which terminates based on size rather than a particular character.

The first payload in the configuration file would therefore be the argument to `system()`, while the second - the one which overwrites the function pointer - would be the address of `system()` itself. With ASLR disabled, that address remained fixed.

![The final Challenge Two exploit.]({{ site.baseurl }}/assets/img/BE2/21-exploit.png)

When run, it worked.

![A shell obtained through the overwritten callback.]({{ site.baseurl }}/assets/img/BE2/22-shell.png)
